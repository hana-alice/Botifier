一、目标与偏好

用户想用桌面机器人检测自己是否靠电脑屏幕太近，持续过近时在电脑上提醒，也可让机器人通过表情、声音或动作提醒。随后希望继续开发有趣的桌面交互。
用户已经选定 M5Stack StackChan，无须重新推荐其他机器人。用户熟悉 C++ 和 UE 底层开发，愿意做二次开发，开发成本不构成主要选型限制。中文沟通，延续具体上下文，避免重复调研已确定的采购内容。
电脑端第一目标按 Windows 考虑，真正实施时确认本机环境。用户最初偏好蓝牙、显示器供电，后来明确 USB/Wi-Fi/蓝牙均可接受。最近建议第一版 USB 直连电脑，兼顾供电、刷写和通信；通信实现仍需开发验证。

二、已选硬件及采购进度

1. M5Stack StackChan 完整机器人，SKU K151 或 K151-R。
   用户在国内淘宝找到的是 K151-R：完整机器人加遥控器套装，机器人部分与 K151 一致，适合本方案。
   遥控器由 StickC-Plus 和 Hat Mini JoyC 组成，原厂支持摇杆及 IMU 姿态遥控，通过 ESP-NOW 控制机器人。测距提醒不依赖遥控器。
   机器人内置 ESP32-S3、屏幕、摄像头、麦克风、扬声器、舵机、触摸及灯光，支持 Wi-Fi 与 BLE。不要把单独的 CoreS3 或 StackChan Core 维修主控当作整机购买。

2. M5Stack Unit ToF4M，SKU U172，VL53L1X 测距模块。
   选择带外壳的完整模块，官方标称量程 4～400 cm，I2C 地址 0x29，视场角可调整。
   完整包装附 HY2.0-4P Grove 连接线 20 cm。

没有项目实现代码、构建产物或实机测试结果需要迁移；此前仅完成方案和源码调查。

三、接线与固定

ToF4M — HY2.0-4P Grove 线 — StackChan 红色 PORT A。
官方 PORT A 引脚：黑 GND、红 5V、黄 SDA/G2、白 SCL/G1；写驱动前与实际硬件/库核对。
StackChan — USB 数据线 — 电脑；优先使用机器人底座 USB-C 接口。
机器人 K151/K151-R 官方完整包装附 USB Type-C 数据线。若电脑放桌下，可补 1.5～2 m USB-A 转 Type-C 数据线；电脑若用 Type-C 口则按接口选线。必须支持数据传输。
机器人包装内另一根 1.25-4P 公母延长线不是连接 ToF4M 的 Grove 线。
第一版不需要额外 MCU、USB 转串口器、蓝牙适配器或焊接。

固定方式尚未定。优先用可移除胶或魔术贴试验，再根据真实尺寸设计 3D 打印支架；没有验证过现成的专用 StackChan-ToF4M 支架。
若传感器固定在显示器附近而机器人会转头，需要留线材余量、限制转动，避免拉扯和缠绕；20 cm 线不一定能从显示器上沿到桌面，需先确认布局。
若模块随头部移动，应只在朝向用户且姿态稳定时判断距离，转动期间暂停或标记无效。
ToF 测到的是传感器到目标表面的距离，不自动等于眼睛到屏幕的距离。需要位置校准、有效读数过滤及遮挡处理。

四、软件路线：此前的研究结论

优先在 M5Stack 官方出厂固件基础上开发，尽量保留现有机器人功能。不要默认刷 Arduino 示例、UiFlow 或社区固件之后仍有原厂全部功能。

官方仓库：
https://github.com/m5stack/StackChan
官方 BSP：
https://github.com/m5stack/StackChan-BSP

此前调查过官方源码快照 eff0d6b（2026-10-22，提交说明为准备 1.2.8 开源版本）。以下是该快照的观察，不保证当前 main 完全一致，接手后核对实际源码：

- 仓库包含 firmware/、app/、server/、remote/。
- 出厂固件使用 C/C++ 和 ESP-IDF；当时 README 指定 ESP-IDF 5.5.4。不是以 Arduino/PlatformIO 为原厂构建入口。
- 当时构建流程为进入 firmware，执行 python3 ./fetch_repos.py 拉取固定依赖，再 idf.py build，随后按设备串口刷写。尚未实际执行编译，不能声称构建成功。
- firmware/main/stackchan/stackchan.h 提供 avatar、motion、灯光、modifier 以及 JSON 更新等接口，适合添加表情和动作。
- firmware/main/main.cpp 中普通菜单由 Mooncake 应用框架运行；进入 XiaoZhi AI 模式时会卸载这些菜单应用并进入另一生命周期。
- 因此持续距离检测不能只写成普通菜单 App；应考虑独立 FreeRTOS 服务/任务或合适的 HAL 层服务，确保 AI 模式也能工作。
- firmware/main/hal/hal.cpp 已有提醒显示、提示音及 StackChan 更新任务路径，可评估复用，但需要处理 UI 锁、音频抢占和任务并发。
- firmware/main/hal/hal_app_center.cpp 的应用启动走 OTA 更新路径。App Center 的下载项不能当作可与出厂功能同时运行的插件。
- 官方 app 使用 Flutter，server 使用 Go；原厂云端、账号绑定、XiaoZhi 服务及其配置是单独问题。仓库开放不代表所有云服务都可原样免费自建。第一版距离判断和本地通知可独立于云端设计。
- 另有社区路线 https://github.com/stack-chan/stack-chan ，支持 JavaScript 等玩法，但替换原厂固件；当前没有选择切换到该路线。

此前调查目录位于远端临时环境，不在用户电脑中。接手本地工作需要重新克隆官方仓库，不能假设已存在源码或 ESP-IDF 工具链。

五、第一版建议范围（待实施，阈值待调试）

1. 可靠采集 ToF4M 距离和测量状态，先能在日志中观察。
2. 可配置距离阈值、连续过近持续时间、提醒冷却时间。
3. 去抖/滤波、恢复滞回；无效读数和无人/遮挡情况不直接按过近触发。
4. 过近持续达到阈值后，机器人显示提醒表情并可发声；声音应能关闭。
5. Windows 端接收事件并弹出通知，提供暂停、阈值配置和连接状态。
6. 第一版优先 USB；确认 USB CDC 与现有固件日志/刷写接口的使用方式，应用消息需有可区分的格式。Wi-Fi 或 BLE 可后续增加。
7. 断连恢复、设置持久化、传感器读取不阻塞 UI 和动作。
8. 不使用固定医学阈值来声称能治疗或预防眼病；这是可配置的距离与休息提醒工具。

六、后续可以开发的 idea（不是已实现功能）

- 编译/打包成功或失败时用表情、灯光、动作通知。
- 显示 Codex/其他 Agent 的工作状态。
- 触摸头部确认或暂停提醒，专注计时和休息提示。
- 遥控器按键改成暂停提醒、切换模式、触发动作。
- 自定义表情、动作组合和桌面伙伴性格。
- 后续按需要增加语音控制、PC 联动；复杂模型放在 PC/服务端，ESP32-S3 不作为通用 Linux 或大模型本地运行平台。

七、建议从哪里继续

先读本文件及用户当前目录的项目说明，检查目录已有内容与 Git 状态。不要覆盖已有工程。
确认硬件是否到货以及实际使用 Windows 原生还是 WSL；不依赖这些信息的源码核对和构建准备可以先做。
建议第一里程碑：克隆/使用官方源码、记录版本、按 README 获取依赖并尝试原版构建，再添加最小 ToF 读取与事件接口。保持改动小且可回退，不先实现一整套远程云后台。
硬件尚未连接时，可用模拟读数验证提醒状态机和电脑端；明确区分模拟测试、构建成功和实机验证。
实际接线、机器人摆放和测量需要用户在本地完成；Codex 负责代码、构建命令、日志分析和迭代，不提前承诺未经测试的精度或稳定性。
